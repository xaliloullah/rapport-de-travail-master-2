1. Objectif et contexte

AWS CodeDeploy automatise la distribution d'une version applicative vers des instances EC2, des serveurs on-premises ou d'autres cibles supportées. Le service sépare la préparation de l'artefact de son déploiement.

  • Installer l'agent sur une instance cible.
  • Définir les fichiers et scripts de déploiement.
  • Créer une application et un groupe de déploiement.
  • Exécuter un déploiement contrôlé et diagnostiquer les échecs.

2. Architecture CodeDeploy

Le flux est : source → révision → CodeDeploy → groupe de déploiement → agent → hooks → validation.

ComposantResponsabilité
RevisionVersion empaquetée de l'application.
ApplicationConteneur logique regroupant les déploiements.
Deployment groupDéfinit les instances cibles et la stratégie.
AgentReçoit et exécute les opérations sur l'instance.
appspec.ymlDécrit fichiers, permissions et hooks.

3. appspec.yml

Pour EC2/on-premises, appspec.yml est le fichier de contrôle du déploiement.

version: 0.0 os: linux files: - source: / destination: /opt/myapp overwrite: true hooks: ApplicationStop: - location: scripts/stop.sh timeout: 60 runas: root ApplicationStart: - location: scripts/start.sh timeout: 60 runas: root ValidateService: - location: scripts/health.sh timeout: 60 runas: root
Attention : la syntaxe des hooks et les chemins doivent correspondre exactement à la structure de la révision.

4. Installation et vérification de l'agent

L'agent doit être actif sur chaque cible.

# Ubuntu/Debian sudo apt update sudo apt install -y ruby wget cd /home/ubuntu wget https://aws-codedeploy-us-east-1.s3.amazonaws.com/latest/install chmod +x install sudo ./install auto sudo systemctl enable --now codedeploy-agent # Vérification sudo systemctl status codedeploy-agent sudo tail -f /var/log/aws/codedeploy-agent/codedeploy-agent.log

5. Rôles IAM

Deux responsabilités doivent être distinguées : le rôle de service utilisé par CodeDeploy et le rôle d'instance attaché à l'EC2.

  • Le rôle de service autorise CodeDeploy à gérer le déploiement.
  • Le rôle d'instance permet à l'agent d'accéder aux ressources nécessaires, notamment au stockage de la révision.
Principe du moindre privilège : ne pas utiliser un rôle administrateur global. Accorder uniquement les actions et ressources nécessaires.

6. Création de l'application CodeDeploy

  1. Ouvrir CodeDeploy.
  2. Créer une application.
  3. Choisir la plateforme EC2/On-premises.
  4. Donner un nom stable, par exemple m2-webapp.

L'application est ensuite associée à un ou plusieurs groupes de déploiement.

7. Groupe de déploiement

Le groupe sélectionne les instances cibles via des tags ou d'autres mécanismes de ciblage. Il définit également le rôle de service et la configuration du déploiement.

ParamètreExemple
TagEnvironment=staging
StratégieIn-place ou Blue/Green selon l'architecture
AlarmesCloudWatch pour déclencher un arrêt/rollback

8. Préparation d'une révision

La révision doit contenir l'application et appspec.yml.

myapp/ ├── appspec.yml ├── application.jar └── scripts/ ├── stop.sh ├── start.sh └── health.sh zip -r myapp.zip myapp/*

Le paquet peut ensuite être stocké dans un emplacement compatible, par exemple un bucket S3.

9. Déploiement

  1. Créer une nouvelle révision.
  2. Sélectionner la source.
  3. Sélectionner le groupe de déploiement.
  4. Lancer le déploiement.
  5. Observer chaque instance et chaque lifecycle event.
Résultat attendu : la révision est téléchargée, les fichiers sont installés, les hooks s'exécutent et ValidateService confirme le bon fonctionnement.

10. Lifecycle hooks

Les hooks permettent d'insérer des opérations dans le cycle de déploiement.

#!/bin/bash set -e sudo systemctl stop myapp || true sudo cp /opt/myapp/application.jar /opt/myapp/releases/application.jar sudo systemctl start myapp curl --fail http://localhost:8080/health
Bonne pratique : rendre les scripts idempotents et faire échouer explicitement le script en cas d'erreur.

11. Rollback et diagnostic

En cas d'échec, examiner d'abord l'événement précis du déploiement puis les logs de l'agent.

sudo tail -n 200 /var/log/aws/codedeploy-agent/codedeploy-agent.log sudo systemctl status codedeploy-agent sudo journalctl -u codedeploy-agent --no-pager
  • Erreur IAM → vérifier le rôle et les permissions.
  • Erreur de hook → exécuter le script manuellement sur l'instance.
  • Fichier absent → vérifier la structure de la révision.
  • Application indisponible → vérifier le service et les ports.

12. Sécurité et bonnes pratiques

  • Utiliser IAM avec le moindre privilège.
  • Ne jamais stocker de secrets dans l'archive.
  • Utiliser Secrets Manager ou Parameter Store pour les secrets.
  • Mettre en place des alarmes CloudWatch.
  • Tester les déploiements en staging avant production.
  • Préférer une stratégie progressive lorsque l'application le permet.
  • Conserver les logs pour l'audit.

13. Checklist

  • [ ] Agent installé et actif
  • [ ] Rôle IAM configuré
  • [ ] Application créée
  • [ ] Groupe de déploiement créé
  • [ ] appspec.yml validé
  • [ ] Scripts exécutables
  • [ ] Révision empaquetée
  • [ ] Déploiement staging réussi
  • [ ] Validation de service réussie
  • [ ] Procédure de rollback testée

14. Conclusion

CodeDeploy fournit la brique de déploiement automatisé d'une chaîne DevOps AWS. La qualité du résultat dépend autant de l'agent et de l'IAM que de la qualité du paquet et des scripts de lifecycle.

Associé à CodeBuild et CodePipeline, CodeDeploy permet de construire une chaîne allant du commit jusqu'au déploiement avec des contrôles et des mécanismes de rollback.
