1. Objectif et contexte

AWS CodeBuild est un service managé de compilation et de test. Il fournit un environnement de build éphémère dans lequel le code source est récupéré, les dépendances sont installées, les tests sont exécutés et les artefacts sont produits.

  • Automatiser la compilation et les tests.
  • Éviter de maintenir un serveur Jenkins uniquement pour le build.
  • Produire des artefacts reproductibles.
  • Préparer l'intégration avec CodePipeline, CodeDeploy ou d'autres outils CI/CD.
Principe : CodeBuild ne remplace pas Git ni le déploiement. Il constitue la brique build/test/package d'une chaîne CI/CD.

2. Architecture et concepts

Point important : les versions de runtime doivent être choisies selon l'image CodeBuild utilisée. Éviter de recopier aveuglément une version ancienne de Java ou Python.

3. Construire un buildspec.yml

Le fichier est placé à la racine du dépôt source. Il décrit les phases install, pre_build, build et post_build, ainsi que les artefacts et rapports.

version: 0.2 phases: install: runtime-versions: java: corretto17 commands: - java -version - mvn -version pre_build: commands: - echo "Préparation du build" - mvn -B clean build: commands: - echo "Compilation et tests" - mvn -B verify post_build: commands: - echo "Build terminé" artifacts: files: - target/*.jar discard-paths: no reports: junit-reports: files: - 'target/surefire-reports/*.xml' file-format: JUNITXML cache: paths: - '/root/.m2/**/*'
Lecture : verify permet d'exécuter le cycle Maven jusqu'aux vérifications. Le bloc artifacts déclare les fichiers à conserver et reports permet de publier les résultats de tests.

4. Création du projet CodeBuild

  1. Ouvrir AWS CodeBuild.
  2. Choisir Create build project.
  3. Définir un nom explicite, par exemple m2-application-build.
  4. Sélectionner la source.
  5. Choisir une image CodeBuild maintenue et le runtime adapté.
  6. Associer un rôle de service IAM.
  7. Configurer les artefacts et les logs.
  8. Créer le projet puis lancer un premier build.

5. Configuration de la source

La source doit contenir le code et, idéalement, le buildspec.yml. Pour un projet Git, le commit déclencheur doit être identifiable afin de pouvoir reproduire le build.

Bon réflexe : versionner le buildspec avec le code. Le pipeline et les règles de compilation deviennent ainsi auditable et reproductible.

6. Rôle IAM du service

CodeBuild utilise un rôle IAM assumé par le service. Ce rôle doit accorder uniquement les permissions nécessaires : lecture de la source, accès aux artefacts S3, écriture des logs CloudWatch Logs et accès réseau éventuel.

{ "Version": "2012-10-17", "Statement": [ { "Effect": "Allow", "Action": ["logs:CreateLogGroup", "logs:CreateLogStream", "logs:PutLogEvents"], "Resource": "*" } ] }
Sécurité : ne pas attribuer AdministratorAccess au rôle CodeBuild par facilité. Les accès S3, Secrets Manager, ECR ou VPC doivent être ciblés sur les ressources réellement utilisées.

7. Exécution et analyse d'un build

Lors du lancement, CodeBuild récupère la source, prépare l'environnement, exécute le buildspec puis publie les résultats. Il faut contrôler successivement :

  1. La phase de téléchargement de la source.
  2. L'installation des runtimes et dépendances.
  3. La phase de tests.
  4. La création des artefacts.
  5. Le statut final SUCCEEDED ou FAILED.
Diagnostic : en cas d'échec, commencer par la première erreur réelle dans les logs plutôt que par la dernière ligne affichée.

8. Artifacts et rapports

Les artefacts permettent de conserver le résultat du build pour l'étape suivante. Un JAR peut être stocké dans S3 puis consommé par CodeDeploy ou CodePipeline.

artifacts: files: - target/*.jar name: application-${CODEBUILD_BUILD_NUMBER}.zip

Les rapports de tests doivent être séparés des artefacts applicatifs afin de conserver une visibilité sur la qualité du build.

9. Tests automatisés

Un build réussi ne signifie pas qu'une application est correcte. Les tests unitaires et d'intégration doivent être exécutés avant la génération finale de l'artefact.

mvn -B test mvn -B verify
  • Échec d'un test → build en échec.
  • Rapports JUnit → visibilité dans CodeBuild.
  • Tests de sécurité → peuvent être ajoutés au pipeline.

10. Intégration CI/CD

Une chaîne typique est :

Git → CodeCommit/GitHub → CodeBuild → artefact S3/ECR → CodeDeploy → EC2/ECS/Lambda.

CodePipeline peut orchestrer ces étapes et déclencher CodeBuild à chaque modification du dépôt. CodeBuild doit rester spécialisé dans le build et les tests.

12. Sécurité et bonnes pratiques

  • Appliquer le moindre privilège IAM.
  • Ne jamais mettre de secrets dans buildspec.yml ou Git.
  • Utiliser Secrets Manager ou Parameter Store lorsque nécessaire.
  • Épingler les versions importantes pour obtenir des builds reproductibles.
  • Conserver les logs et rapports nécessaires à l'audit.
  • Utiliser des environnements séparés pour développement, recette et production.
  • Nettoyer les anciens artefacts selon une politique de rétention.

13. Checklist

  • [ ] Source configurée
  • [ ] buildspec.yml versionné
  • [ ] Runtime validé
  • [ ] Rôle IAM à privilèges minimaux
  • [ ] Logs activés
  • [ ] Tests automatisés
  • [ ] Artifacts configurés
  • [ ] Premier build réussi
  • [ ] Échec volontaire testé pour valider le pipeline

14. Conclusion

Ce travail montre comment CodeBuild automatise la compilation, les tests et la production d'artefacts sans maintenir une infrastructure de build permanente. La valeur de CodeBuild apparaît surtout lorsqu'il est intégré à une chaîne CI/CD complète et sécurisé par IAM.

La prochaine étape logique est de relier CodeBuild à CodePipeline puis CodeDeploy afin d'obtenir une chaîne automatisée allant du commit jusqu'au déploiement contrôlé.
