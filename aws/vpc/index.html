1. Objectifs et contexte

Ce travail pratique présente la conception et la mise en œuvre d'un Amazon Virtual Private Cloud (VPC). L'objectif est de construire une architecture réseau maîtrisée permettant de séparer les ressources publiques, privées et éventuellement isolées.

À l'issue de la réalisation, l'étudiant doit être capable de :

  • concevoir un espace d'adressage IPv4 en notation CIDR ;
  • créer un VPC et des sous-réseaux répartis sur plusieurs Availability Zones ;
  • configurer une Internet Gateway et des tables de routage ;
  • comprendre et mettre en œuvre un NAT Gateway pour les sorties Internet des ressources privées ;
  • différencier Security Groups et Network ACLs ;
  • tester la connectivité et diagnostiquer un problème de routage ou de filtrage.
Résultat attendu : une topologie VPC comprenant des sous-réseaux publics et privés, avec des routes explicites et des contrôles réseau adaptés.

2. Prérequis

  • Compte AWS actif et région choisie.
  • AWS CLI v2 installée et configurée, ou accès à AWS CloudShell.
  • Connaissances de base en IPv4, CIDR, routage et pare-feu.
  • Autorisations IAM permettant de créer et gérer les ressources VPC nécessaires.
  • Une paire de clés EC2 si une instance de test doit être administrée en SSH.

Vérification de l'identité AWS

aws sts get-caller-identity aws configure get region
Important : ne placez jamais des clés d'accès AWS, des secrets ou des fichiers .pem dans le dépôt Git.

3. Concepts et architecture

ComposantRôle
VPCRéseau virtuel isolé dans une région AWS, défini notamment par un bloc CIDR.
SubnetSubdivision du VPC associée à une Availability Zone.
Internet GatewayPermet la connectivité Internet des ressources disposant d'un chemin de routage et d'une adresse publique.
NAT GatewayPermet aux ressources privées d'initier des connexions IPv4 vers l'extérieur sans recevoir de connexions Internet initiées vers elles.
Route TableDétermine la cible vers laquelle le trafic correspondant à une destination doit être envoyé.
Security GroupPare-feu stateful associé aux interfaces réseau des ressources.
Network ACLFiltrage stateless appliqué au niveau du sous-réseau.
VPC Flow LogsJournalisation des flux réseau pour l'analyse et le diagnostic.

Topologie de référence

Internet | Internet Gateway | +--------------+--------------+ | | Public Subnet A Public Subnet B | | ALB / NAT GW ALB / NAT GW | | Private Subnet A Private Subnet B | | Application tier Application tier | | Data tier / DB Data tier / DB VPC : 10.0.0.0/16 Public A : 10.0.1.0/24 Public B : 10.0.2.0/24 Private A: 10.0.11.0/24 Private B: 10.0.12.0/24

Un subnet est dit public lorsqu'il possède une route vers une Internet Gateway. Une ressource IPv4 doit également disposer d'une adresse IPv4 publique ou Elastic IP pour communiquer directement avec Internet. citeturn0search3turn0search7

4. Installation et configuration

4.1 Création du VPC

aws ec2 create-vpc \ --cidr-block 10.0.0.0/16 \ --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=master2-vpc}]'

Conserver l'identifiant retourné, par exemple vpc-xxxxxxxx. Le bloc /16 offre 65 536 adresses IPv4 théoriques ; AWS réserve toutefois certaines adresses dans chaque subnet.

4.2 Création des sous-réseaux

aws ec2 create-subnet --vpc-id vpc-xxxxxxxx --cidr-block 10.0.1.0/24 --availability-zone <AZ-A> --tag-specifications 'ResourceType=subnet,Tags=[{Key=Name,Value=public-a}]' aws ec2 create-subnet --vpc-id vpc-xxxxxxxx --cidr-block 10.0.2.0/24 --availability-zone <AZ-B> --tag-specifications 'ResourceType=subnet,Tags=[{Key=Name,Value=public-b}]' aws ec2 create-subnet --vpc-id vpc-xxxxxxxx --cidr-block 10.0.11.0/24 --availability-zone <AZ-A> --tag-specifications 'ResourceType=subnet,Tags=[{Key=Name,Value=private-a}]' aws ec2 create-subnet --vpc-id vpc-xxxxxxxx --cidr-block 10.0.12.0/24 --availability-zone <AZ-B> --tag-specifications 'ResourceType=subnet,Tags=[{Key=Name,Value=private-b}]'

4.3 Internet Gateway

aws ec2 create-internet-gateway \ --tag-specifications 'ResourceType=internet-gateway,Tags=[{Key=Name,Value=master2-igw}]' aws ec2 attach-internet-gateway \ --vpc-id vpc-xxxxxxxx \ --internet-gateway-id igw-xxxxxxxx

4.4 Routage public

aws ec2 create-route-table --vpc-id vpc-xxxxxxxx aws ec2 create-route --route-table-id rtb-public --destination-cidr-block 0.0.0.0/0 --gateway-id igw-xxxxxxxx aws ec2 associate-route-table --route-table-id rtb-public --subnet-id subnet-public-a

La route 0.0.0.0/0 → igw-xxxxxxxx fournit le chemin IPv4 par défaut vers Internet. citeturn0search10

5. Réalisation pratique

5.1 Mise en place du NAT Gateway

# Allouer une Elastic IP aws ec2 allocate-address --domain vpc # Créer le NAT Gateway dans un subnet public aws ec2 create-nat-gateway \ --subnet-id subnet-public-a \ --allocation-id eipalloc-xxxxxxxx \ --tag-specifications 'ResourceType=nat-gateway,Tags=[{Key=Name,Value=master2-nat-a}]' # Vérifier son état aws ec2 describe-nat-gateways --nat-gateway-ids nat-xxxxxxxx \ --query 'NatGateways[0].[NatGatewayId,State,ConnectivityType]' \ --output table

Le NAT Gateway public doit être placé dans un subnet public disposant lui-même d'une route vers l'Internet Gateway. Le subnet privé doit ensuite utiliser le NAT Gateway comme cible de sa route par défaut. citeturn0search5turn0search4

5.2 Routage privé

aws ec2 create-route-table --vpc-id vpc-xxxxxxxx aws ec2 create-route \ --route-table-id rtb-private \ --destination-cidr-block 0.0.0.0/0 \ --nat-gateway-id nat-xxxxxxxx aws ec2 associate-route-table \ --route-table-id rtb-private \ --subnet-id subnet-private-a

5.3 Association des ressources

Associer explicitement chaque subnet à la route table correspondant à son rôle. Une route table peut être associée à plusieurs subnets, mais un subnet ne possède qu'une association de route table effective à un instant donné. citeturn0search7

7. Vérifications et tests

7.1 Vérifier la topologie

aws ec2 describe-vpcs --vpc-ids vpc-xxxxxxxx --output table aws ec2 describe-subnets --filters "Name=vpc-id,Values=vpc-xxxxxxxx" --output table aws ec2 describe-route-tables --filters "Name=vpc-id,Values=vpc-xxxxxxxx" --output table

7.2 Vérifier l'Internet Gateway

aws ec2 describe-internet-gateways \ --filters "Name=attachment.vpc-id,Values=vpc-xxxxxxxx" \ --query 'InternetGateways[].InternetGatewayId' \ --output text

7.3 Vérifier le NAT Gateway

aws ec2 describe-nat-gateways \ --filter "Name=vpc-id,Values=vpc-xxxxxxxx" \ --query 'NatGateways[].{Id:NatGatewayId,State:State,Subnet:SubnetId}' \ --output table

7.4 Test depuis une instance

# Dans une instance privée disposant d'un accès NAT curl -I https://aws.amazon.com # Vérifier la route locale ip route
Critères de réussite : les ressources publiques suivent la route vers l'IGW ; les ressources privées utilisent la route vers le NAT pour les connexions sortantes ; aucune route Internet directe ne doit exister dans le subnet privé.

8. Dépannage

SymptômeDiagnosticCorrection
Instance publique sans InternetVérifier route table, IGW et adresse publique.Ajouter la route 0.0.0.0/0 → IGW et vérifier l'IPv4 publique.
Instance privée sans InternetVérifier état du NAT, routes public/privé et NACL.NAT dans un subnet public, route privée vers NAT, route NAT vers IGW.
SSH impossibleVérifier SG, NACL, route et adresse publique.Autoriser TCP/22 depuis l'IP d'administration et vérifier le chemin réseau.
HTTP bloquéVérifier SG/NACL et service Web.Autoriser TCP/80 ou TCP/443 selon le service.
NAT en état faileddescribe-nat-gateways et événements de création.Vérifier subnet public, Elastic IP et routage.
Trafic inattendu bloquéComparer Security Group, NACL et route table.Corriger la règle la plus restrictive sans ouvrir inutilement le réseau.
Principe de diagnostic : vérifier successivement route → gateway/NAT → NACL → Security Group → système/service. AWS recommande également les VPC Flow Logs pour analyser certains problèmes de trafic. citeturn0search4turn0search8

9. Sécurité et bonnes pratiques

  • Segmentation : placer les ressources qui ne doivent pas être accessibles directement depuis Internet dans des subnets privés.
  • Security Groups : les utiliser comme mécanisme principal de filtrage au niveau des ressources.
  • NACL : les utiliser comme couche complémentaire de défense au niveau des subnets.
  • SSH : limiter TCP/22 à des sources d'administration connues ou privilégier AWS Systems Manager lorsque l'architecture le permet.
  • Routage : conserver uniquement les routes nécessaires au fonctionnement de l'application.
  • Multi-AZ : répartir les composants critiques sur plusieurs Availability Zones lorsque la disponibilité l'exige.
  • Flow Logs : activer VPC Flow Logs pour améliorer l'observabilité et le diagnostic.
  • NAT : pour une architecture de production multi-AZ, dimensionner et répartir les NAT Gateways selon les exigences de disponibilité et de coût.
  • IAM : appliquer le moindre privilège aux utilisateurs, rôles et automatisations qui administrent le VPC.
  • Coûts : supprimer les NAT Gateways, Elastic IP et autres ressources de TP lorsqu'elles ne sont plus nécessaires.
Attention : un subnet privé n'est pas synonyme de sécurité absolue. Les routes, Security Groups, NACLs, IAM et contrôles de l'hôte doivent être cohérents. citeturn0search8

10. Checklist

  • [ ] CIDR du VPC défini et non chevauché avec les réseaux nécessaires
  • [ ] VPC créé
  • [ ] Subnets publics répartis sur plusieurs AZ si nécessaire
  • [ ] Subnets privés créés
  • [ ] Internet Gateway attachée au VPC
  • [ ] Route table publique associée aux subnets publics
  • [ ] Route 0.0.0.0/0 → IGW validée
  • [ ] NAT Gateway créé dans un subnet public si nécessaire
  • [ ] Route table privée associée aux subnets privés
  • [ ] Route 0.0.0.0/0 → NAT Gateway validée
  • [ ] Security Groups configurés selon le moindre privilège
  • [ ] NACLs vérifiées
  • [ ] Tests de connectivité réalisés
  • [ ] VPC Flow Logs envisagés ou activés selon le besoin
  • [ ] Ressources de test supprimées après le TP pour maîtriser les coûts

11. Conclusion

Ce travail pratique a permis de concevoir et de mettre en œuvre un VPC AWS structuré autour de sous-réseaux publics et privés, de tables de routage, d'une Internet Gateway et, lorsque nécessaire, d'un NAT Gateway.

L'étude montre que la connectivité AWS ne dépend pas uniquement d'un pare-feu : elle résulte de l'interaction entre le plan d'adressage, les associations de subnets, les routes, les gateways, les Security Groups et les Network ACLs. Les VPC Flow Logs complètent cette architecture par une capacité d'observation des flux.

Pour une architecture de production, cette base peut être complétée par un Application Load Balancer, des services privés, des VPC endpoints, une supervision centralisée, une connexion VPN ou Direct Connect et une automatisation Infrastructure as Code.
