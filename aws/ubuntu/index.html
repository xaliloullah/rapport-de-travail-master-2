1. Objectifs et contexte

Ce travail pratique présente la mise en place d’un serveur Ubuntu Server dans Amazon EC2, puis son administration avec l’AWS Command Line Interface (AWS CLI). L’objectif est de comprendre le lien entre calcul, réseau, stockage, identité IAM et administration automatisable.

  • Créer une instance EC2 à partir d’une AMI Ubuntu LTS.
  • Configurer VPC, subnet, Security Group, stockage EBS et accès SSH.
  • Installer AWS CLI v2 et vérifier son fonctionnement.
  • Utiliser de préférence un rôle IAM attaché à l’instance.
  • Valider la connectivité, l’identité AWS et les permissions.
Principe : EC2 fournit le calcul, Ubuntu fournit le système, VPC encadre le réseau, IAM contrôle les API AWS et AWS CLI fournit l’interface d’administration. Sur EC2, les identifiants temporaires d’un rôle d’instance sont préférables aux clés statiques.

4. Installation et configuration

4.1 Création via la console EC2

  1. Choisir Ubuntu Server 24.04 LTS.
  2. Sélectionner une instance adaptée au TP.
  3. Choisir/créer la Key Pair.
  4. Choisir VPC et subnet.
  5. Autoriser TCP/22 uniquement depuis l’IP d’administration.
  6. Configurer le volume EBS et le tag Name=Ubuntu-M2-UDB.
  7. Lancer l’instance et relever son IP publique si SSH direct est utilisé.

4.2 Connexion SSH

# Linux/macOS chmod 400 mykey.pem ssh -i mykey.pem ubuntu@PUBLIC_IP # Windows PowerShell ssh -i .\mykey.pem ubuntu@PUBLIC_IP

Le compte initial d’une image Ubuntu EC2 est généralement ubuntu. La clé privée ne doit jamais être publiée.

4.3 Préparation du système

sudo apt update sudo apt upgrade -y sudo reboot

5. Réalisation pratique

5.1 Diagnostic initial

hostnamectl cat /etc/os-release uname -m ip addr ip route df -h free -h

5.2 Installation d’AWS CLI v2

AWS fournit actuellement un installateur Linux officiel. Pour une installation système :

sudo apt update sudo apt install -y curl curl -fsSL https://awscli.amazonaws.com/v2/install.sh | sudo bash -s -- --system aws --version

Pour une installation reproductible avec contrôle de version, l’archive officielle awscliv2.zip peut être utilisée. Adapter l’archive à x86_64 ou aarch64 selon uname -m.

5.3 Identité IAM de l’instance

Attacher un IAM Role au profil d’instance permet à AWS CLI de récupérer des identifiants temporaires sans stocker de clés permanentes.

aws sts get-caller-identity aws configure set region us-east-1 aws ec2 describe-instances --max-results 5
À éviter : mettre une Access Key dans Git, un script ou une image EC2. Utiliser un rôle d’instance ou, lorsque nécessaire, un profil IAM géré selon le moindre privilège.

5.4 Création EC2 par CLI — exemple

# Exemple : remplacer les identifiants par ceux de votre environnement aws ec2 run-instances \ --image-id ami-XXXXXXXX \ --instance-type t3.micro \ --key-name ma-cle-ec2 \ --security-group-ids sg-XXXXXXXX \ --subnet-id subnet-XXXXXXXX \ --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=Ubuntu-M2-UDB}]'

--image-id identifie l’AMI, --instance-type définit les ressources, tandis que subnet et Security Group déterminent le rattachement réseau. Les identifiants sont volontairement des placeholders : ils dépendent de la région et du compte.

9. Sécurité et bonnes pratiques

  • Activer MFA sur les identités humaines.
  • Appliquer le moindre privilège IAM.
  • Préférer les rôles IAM et identifiants temporaires sur EC2.
  • Ne jamais publier clés AWS ou clés SSH privées dans Git.
  • Limiter TCP/22 à un réseau d’administration connu.
  • Privilégier Systems Manager Session Manager lorsque possible afin d’éviter une exposition SSH directe.
  • Maintenir Ubuntu et les composants à jour.
  • Chiffrer les volumes EBS et maîtriser leur cycle de vie.
  • Superviser l’instance et conserver les journaux utiles.
  • Arrêter/supprimer les ressources de TP inutilisées pour éviter les coûts.
Production : une instance privée administrée par Systems Manager et protégée par une architecture réseau contrôlée est généralement préférable à une instance exposant SSH directement sur Internet.

11. Conclusion

Ce travail pratique a permis de mettre en œuvre une chaîne complète allant du lancement d’un serveur Ubuntu sur Amazon EC2 jusqu’à son administration avec AWS CLI. La démarche couvre les dimensions système, réseau, stockage, identité et automatisation nécessaires à l’exploitation d’une instance cloud.

La séparation des responsabilités est essentielle : EC2 fournit le calcul, VPC/Security Groups encadrent le réseau, IAM contrôle les autorisations et AWS CLI fournit l’interface d’administration. Cette base prépare les travaux DevOps suivants : serveur Web, CI/CD, automatisation et supervision.
