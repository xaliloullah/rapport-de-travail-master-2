1. Objectifs et contexte

Ce travail pratique présente la mise en place d’un serveur Ubuntu Server dans Amazon EC2, puis l’installation et la configuration de l’AWS Command Line Interface (AWS CLI). L’objectif est de disposer d’une machine Linux administrable à distance et capable d’interroger les services AWS de manière sécurisée.

  • Créer et démarrer une instance EC2 à partir d’une AMI Ubuntu LTS.
  • Configurer le stockage, les clés SSH et le Security Group.
  • Se connecter au serveur avec SSH.
  • Installer AWS CLI v2 et vérifier son fonctionnement.
  • Utiliser une identité IAM adaptée pour les appels AWS depuis l’instance.
  • Valider la connectivité, les permissions et l’état du système.
Contexte : EC2 fournit le calcul tandis qu’Ubuntu fournit l’environnement système. AWS CLI constitue l’interface d’administration en ligne de commande. Dans une architecture professionnelle, l’identité de l’instance doit idéalement être fournie par un rôle IAM attaché au profil d’instance plutôt que par des clés d’accès statiques.

2. Prérequis

2.1 Ressources AWS

  • Compte AWS actif avec MFA activée sur les comptes humains.
  • Région AWS choisie pour le TP, par exemple us-east-1.
  • Permissions permettant de créer ou d’utiliser une instance EC2 et ses ressources associées.
  • Une paire de clés EC2 si l’accès SSH par clé est retenu.

2.2 Poste client

  • Terminal Linux/macOS, PowerShell Windows ou client SSH équivalent.
  • Accès Internet pour joindre l’instance.
  • Clé privée .pem conservée dans un emplacement sécurisé.

L’architecture retenue repose sur EC2, le réseau VPC et les mécanismes IAM d’AWS.

4. Installation et configuration

4.1 Création de l’instance EC2

  1. Ouvrir la console AWS puis le service EC2.
  2. Choisir Ubuntu Server 24.04 LTS comme AMI.
  3. Sélectionner un type d’instance compatible avec le besoin du TP.
  4. Choisir ou créer une paire de clés.
  5. Associer l’instance à un VPC et un subnet appropriés.
  6. Créer un Security Group avec SSH limité à l’adresse IP d’administration.
  7. Ajouter un volume EBS adapté au besoin.
  8. Ajouter le tag Name=Ubuntu-M2-UDB.
  9. Lancer l’instance et relever son adresse IP publique si elle est nécessaire pour SSH.

4.2 Connexion SSH

# Linux/macOS chmod 400 mykey.pem ssh -i mykey.pem ubuntu@PUBLIC_IP # Windows PowerShell ssh -i .\mykey.pem ubuntu@PUBLIC_IP

Le compte initial ubuntu est celui fourni par l’image Ubuntu EC2. La commande chmod 400 limite les permissions de la clé privée sous Linux/macOS.

4.3 Mise à jour du serveur

sudo apt update sudo apt upgrade -y sudo reboot

Après le redémarrage, reconnecter la session SSH avant de poursuivre.

5. Réalisation pratique

5.1 Vérification de l’environnement

hostnamectl cat /etc/os-release uname -m ip addr ip route

Ces commandes permettent d’identifier le système, l’architecture processeur, les interfaces et la route par défaut.

5.2 Installation d’AWS CLI v2

Pour une instance Linux x86_64 :

sudo apt update sudo apt install -y curl unzip curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o "awscliv2.zip" unzip -q awscliv2.zip sudo ./aws/install aws --version

Pour une instance ARM64, utiliser l’archive AWS CLI correspondant à l’architecture aarch64 au lieu de l’archive x86_64.

5.3 Identité AWS

La méthode recommandée sur EC2 consiste à attacher un rôle IAM au profil d’instance. Une fois le rôle correctement configuré, AWS CLI peut récupérer automatiquement des identifiants temporaires.

# Vérifier l’identité utilisée par AWS CLI aws sts get-caller-identity # Définir la région par défaut si nécessaire aws configure set region us-east-1 # Exemple de vérification EC2 aws ec2 describe-instances --max-results 5
À éviter : ne pas placer une clé d’accès IAM permanente dans un script, dans Git ou dans une image de machine. Si une identité utilisateur est réellement nécessaire hors EC2, utiliser un profil AWS CLI géré de manière sécurisée et une politique IAM au moindre privilège.

5.4 Test de stockage

df -h lsblk free -h

On vérifie ainsi l’espace disque, les volumes blocs visibles et la mémoire disponible.

7. Vérifications et tests

7.1 Tests système

systemctl is-system-running systemctl is-active ssh ss -lntp | grep ':22' df -h / free -h

7.2 Test réseau

ip route getent hosts aws.amazon.com curl -I https://aws.amazon.com

7.3 Test AWS CLI

aws --version aws sts get-caller-identity aws ec2 describe-regions --query 'Regions[0:3].[RegionName,OptInStatus]' --output table
Résultat attendu : la version d’AWS CLI est affichée, STS retourne l’identité IAM effective et l’appel EC2 renvoie des données sans erreur d’authentification ou d’autorisation.

7.4 Critères de validation

  • Connexion SSH fonctionnelle.
  • Service SSH actif.
  • Résolution DNS opérationnelle.
  • Accès HTTPS sortant disponible lorsque requis.
  • AWS CLI installé et exécutable.
  • aws sts get-caller-identity retourne le principal attendu.
  • Les appels AWS autorisés par la politique IAM aboutissent.

9. Sécurité et bonnes pratiques

  • Activer MFA sur les identités humaines AWS.
  • Appliquer le principe du moindre privilège avec IAM.
  • Préférer les rôles IAM et les identifiants temporaires sur EC2.
  • Ne jamais publier de clés AWS ou de clés SSH privées dans Git.
  • Limiter le port SSH 22 à une adresse ou un réseau d’administration connu.
  • Utiliser AWS Systems Manager Session Manager lorsque l’architecture permet d’éviter l’exposition SSH.
  • Maintenir Ubuntu et les logiciels à jour.
  • Chiffrer les volumes EBS et contrôler leur cycle de vie.
  • Superviser l’instance avec CloudWatch et conserver les journaux pertinents.
  • Arrêter ou supprimer les ressources de TP inutilisées afin d’éviter les coûts.
Architecture sécurisée : pour un environnement de production, une instance privée sans IP publique, administrée par Systems Manager et placée derrière une architecture réseau contrôlée, est généralement préférable à une exposition directe de SSH sur Internet.

11. Conclusion

Ce travail pratique a permis de mettre en œuvre une chaîne complète allant du lancement d’un serveur Ubuntu sur Amazon EC2 jusqu’à son administration avec AWS CLI. La démarche a couvert les dimensions système, réseau, identité et automatisation nécessaires à l’exploitation d’une instance cloud.

La maîtrise de cette architecture constitue une base importante pour les travaux DevOps suivants : déploiement Web, intégration continue, automatisation avec des scripts, infrastructure as code et supervision.

Le point essentiel retenu est la séparation des responsabilités : EC2 fournit le calcul, VPC et Security Groups encadrent le réseau, IAM contrôle les autorisations et AWS CLI fournit l’interface d’administration. Une configuration professionnelle doit privilégier les identités temporaires, le moindre privilège et une surface réseau minimale.
