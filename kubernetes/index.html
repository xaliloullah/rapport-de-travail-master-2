1. Objectifs et contexte

Ce travail pratique a pour objectif d'étudier Kubernetes, plateforme open source d'orchestration de conteneurs, puis de mettre en œuvre un cluster Linux avec kubeadm, containerd, kubelet et kubectl.

La réalisation repose sur un nœud control plane et au moins un nœud worker. Le control plane expose l'API Kubernetes et coordonne le cluster ; les workers exécutent les charges de travail conteneurisées.

  • Comprendre le rôle de Kubernetes dans une architecture conteneurisée.
  • Identifier les principaux composants du control plane et des workers.
  • Installer un runtime compatible CRI, ici containerd.
  • Installer kubeadm, kubelet et kubectl.
  • Initialiser le control plane et déployer un plugin CNI.
  • Joindre un worker au cluster et vérifier son état.
  • Déployer une application simple afin de valider le fonctionnement.
Cadre technique : Kubernetes recommande kubeadm pour construire un cluster administré soi-même. Les procédures modernes utilisent pkgs.k8s.io ; l'ancien dépôt apt.kubernetes.io est déprécié.

Kubernetes transforme un ensemble de machines en cluster capable d'exécuter et de maintenir des applications conteneurisées selon un état désiré.

4. Installation et configuration

4.1 Préparer chaque nœud

sudo apt-get update
sudo apt-get install -y ca-certificates curl gpg
sudo swapoff -a
sudo sed -i '/[[:space:]]swap[[:space:]]/ s/^/#/' /etc/fstab
cat <
Explications : le swap est désactivé, les modules réseau sont chargés et le routage IPv4 est activé pour préparer le nœud à Kubernetes.

4.2 Installer et configurer containerd

sudo apt-get update
sudo apt-get install -y containerd
sudo mkdir -p /etc/containerd
containerd config default | sudo tee /etc/containerd/config.toml >/dev/null
sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml
sudo systemctl restart containerd
sudo systemctl enable containerd
sudo systemctl status containerd --no-pager
Runtime : Kubernetes utilise le CRI pour communiquer avec un runtime. containerd est compatible avec cette architecture ; Docker Engine seul ne fournit pas directement le CRI attendu.

4.3 Installer kubeadm, kubelet et kubectl

L'ancien dépôt apt.kubernetes.io du rapport précédent est remplacé par pkgs.k8s.io. L'exemple utilise Kubernetes 1.37 ; pour une autre version mineure, remplacer le numéro dans l'URL du dépôt.

sudo mkdir -p -m 755 /etc/apt/keyrings
curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.37/deb/Release.key \
  | sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg
echo 'deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.37/deb/ /' \
  | sudo tee /etc/apt/sources.list.d/kubernetes.list
sudo apt-get update
sudo apt-get install -y kubelet kubeadm kubectl
sudo apt-mark hold kubelet kubeadm kubectl
sudo systemctl enable --now kubelet
kubeadm version
kubelet --version
kubectl version --client
Rôle des outils : kubeadm initialise/rejoint les clusters, kubelet maintient les pods et kubectl dialogue avec l'API Kubernetes.

5. Réalisation pratique

5.1 Initialisation du control plane

Sur k8s-master, initialiser le control plane. Le CIDR ci-dessous correspond au scénario Flannel du TP.

sudo kubeadm init --pod-network-cidr=10.244.0.0/16
Résultat : kubeadm effectue les contrôles préalables, génère les certificats, déploie les composants du control plane et fournit les instructions de configuration de kubectl ainsi que la commande de jonction des workers.

5.2 Configurer kubectl

mkdir -p $HOME/.kube
sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown "$(id -u):$(id -g)" $HOME/.kube/config
kubectl get nodes

5.3 Installer le réseau CNI

Un cluster kubeadm a besoin d'un plugin réseau. L'exemple conserve Flannel afin de rester cohérent avec le TP initial.

kubectl apply -f https://github.com/flannel-io/flannel/releases/latest/download/kube-flannel.yml
kubectl get pods -n kube-flannel
kubectl get nodes
Attention : ne pas déployer plusieurs CNI simultanément dans ce scénario. Le CIDR et la procédure doivent correspondre au plugin retenu.

5.4 Joindre le worker

Sur le worker, exécuter la commande générée par kubeadm init :

sudo kubeadm join 10.0.1.10:6443 \
  --token <TOKEN> \
  --discovery-token-ca-cert-hash sha256:<HASH>
Paramètres : 10.0.1.10:6443 désigne l'API Server ; le token sert à l'amorçage et le hash protège la découverte de l'autorité de certification.

5.5 Déployer une application de test

kubectl create deployment nginx --image=nginx:stable
kubectl expose deployment nginx --port=80 --type=NodePort
kubectl get deployments
kubectl get pods -o wide
kubectl get services

Cette étape valide la chaîne API Kubernetes → scheduler → kubelet → containerd → pod → Service.

7. Vérifications et tests

7.1 État des nœuds

kubectl get nodes -o wide

Les nœuds attendus doivent apparaître avec le statut Ready.

7.2 Pods système

kubectl get pods -n kube-system

7.3 Tester Nginx

kubectl get deployment nginx
kubectl get pods -l app=nginx -o wide
kubectl get service nginx
curl http://<IP_NOEUD>:<NODE_PORT>

Le test est réussi si le Service fournit la réponse HTTP de Nginx et que les pods restent disponibles.

7.4 Vérifier les services système

sudo systemctl status containerd --no-pager
sudo systemctl status kubelet --no-pager
sudo journalctl -u kubelet -n 100 --no-pager

9. Sécurité et bonnes pratiques

9.1 Réseau et pare-feu

Les ports doivent être ouverts uniquement entre les machines et sources nécessaires. Les ports standards comprennent notamment 6443/TCP pour l'API Server, 2379-2380/TCP pour etcd, 10250/TCP pour kubelet et 30000-32767 pour les NodePorts.

sudo ss -lntup
sudo ufw status verbose

9.2 Identité et accès

  • Protéger /etc/kubernetes/admin.conf.
  • Éviter l'utilisation permanente d'un kubeconfig administrateur.
  • Utiliser RBAC avec le moindre privilège.
  • Créer des ServiceAccounts dédiés.

9.3 Images et workloads

  • Utiliser des registres fiables.
  • Épingler les versions des images plutôt que :latest.
  • Scanner les images avant déploiement.
  • Éviter les conteneurs privilégiés sans nécessité.
  • Ne pas stocker de secrets dans les images.

9.4 Maintenance

  • Planifier les mises à niveau de Kubernetes et du runtime.
  • Surveiller CPU, mémoire, disque et réseau.
  • Centraliser les logs et alertes.
  • Sauvegarder les données critiques, notamment etcd selon l'architecture.
Principe fondamental : la sécurité Kubernetes couvre l'identité, le réseau, les images, les workloads, les secrets, les logs et les procédures d'administration.

11. Conclusion

Ce travail pratique a permis de passer d'une présentation générale de Kubernetes à la réalisation d'un cluster fonctionnel reposant sur un control plane et un nœud worker. La démarche a couvert la préparation du système Linux, l'installation de containerd, l'installation de kubeadm/kubelet/kubectl, l'initialisation du control plane, le réseau CNI et l'intégration d'un worker.

Les vérifications réalisées avec kubectl, les journaux de kubelet et de containerd, ainsi que le déploiement d'une application Nginx permettent de valider les principales briques du cluster.

Au-delà de l'installation, Kubernetes impose une démarche d'exploitation structurée : RBAC, segmentation réseau, gestion des secrets, supervision, sauvegarde et mises à jour contrôlées. Le cluster constitue ainsi une base pédagogique pour approfondir Ingress, stockage persistant, Helm, Prometheus/Grafana et les architectures hautement disponibles.

Références techniques : documentation officielle Kubernetes relative à l'installation de kubeadm, la création d'un cluster, l'ajout de workers et les ports réseau.
